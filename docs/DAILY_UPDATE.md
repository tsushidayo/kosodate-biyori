# こそだて日和の毎日の更新

本人だけが閲覧できるSitesとして運用する。共有データの更新先 `/api/update` と `/api/refresh` はそのアクセス制限を前提とする。公開範囲を広げる前に管理者認証を追加する。

1. Sitesの `get_site` でサイトID、公開URL、本人限定の公開範囲を確認する。返された `siwc_bypass_bearer_token` はセッション内だけで保持する。ソースを触る場合は別途 `create_source_repository_write_credential` で最新ソースを取得する。
2. `/api/content` の現状を読み、価格、制度、食事と育児の案内、ニュース、コラム、SNSの話題を公的サイトや出典元で確認する。認証回避はしない。記事や投稿の全文は転載しない。SNSの数値を確認できない話題をバズとは呼ばない。
3. 商品は同じ型番・容量・個数を区別し、送料、最低注文額、クーポン条件、在庫、確認時刻を記録する。通販の価格を店頭価格として記録しない。ローカル店は店舗名、所在地、出典、確認日がある情報だけを比較する。価格を再確認できない場合は元の確認日を保ち、未確認とする。「全国最安」と断定しない。
4. 食事、健康、制度の変更は公的な一次資料で確認し、該当セクションを更新する。制度の自治体、対象者、申請先を省略しない。異常時や緊急時の案内を体験談だけで変更しない。
5. `scripts/update-site.mjs` にJSONを標準入力で渡す。形式は `{ "url": "<公開URL>", "token": "<セッション内の値>", "updates": [{"section":"shop","path":"<作成したJSONの絶対パス>"}], "refreshFeeds": true }`。sectionは care / shop / editorial / feeds。秘密を引数、ファイル、ログ、タスクのプロンプトへ保存しない。更新対象がなくてもRSSを取得する。
6. スクリプト末尾の `/api/status` 読み戻しで `storageAvailable: true`、更新番号、件数を確認する。取得失敗した出典、古い価格、確認できなかったページを結果に含める。

通常の更新はD1のデータだけを変更し、再公開しない。RSSはソースに登録されたURLだけを取得する。ソースの変更が必要な場合はSitesの保存・公開手順を使う。既存のXサイトのリポジトリには書き込まない。

## API

- GET `/api/content`: care / shop / editorial / feeds とセクションごとの更新日・更新番号・保存先の状態。
- POST `/api/update`: `{section,payload,expectedRevision?}` または `{updates:[...]}`。完全なセクションの内容を保存する。
- POST `/api/refresh`: 登録した公開RSSから育児関連の記事を追加する。失敗時は元の記事を維持する。
- GET `/api/status`: 保存先・更新日・更新番号・件数を読み戻す。
- GET / PUT `/api/profile`: Sitesの利用者IDごとの日付・保存記事・完了した項目・価格の通知条件。PUTは `{profile,expectedRevision?}`。未ログインは401。別の端末での上書きを防ぐためGETのrevisionをexpectedRevisionに渡す。

ブラウザーの通知はページを開いたときの比較結果に基づく。閉じているブラウザーへの配信やメール送信は、このAPIでは提供しない。

価格の自動取得を補助する場合は `scripts/price-refresh.mjs` を使う。ただし同一商品の個数・送料・税込表示・在庫が一致することを再確認し、判別できないものは採用しない。定期便・クーポンは検索で別途確認する。サイトの最安候補からは48時間を超えた価格を外す。

毎日の検索は全ページが対象。新しい出典や自治体があれば対象へ追加する。ページを検索しただけでは確認日を新しくせず、本文や価格を実際に確認できた項目だけ更新する。配信サービス未接続の背景通知・メール配信、計測できないSNSの人気順を完了扱いしない。

## 価格の追加方針
商品ごとに異なる販売先を増やし、確認できる商品は上位10店を比べられるようにする。10店に満たない場合も架空の価格や空の順位は追加しない。配送と店舗受取を同じ販売先の別の買い方として扱い、販売先の数を水増ししない。JAN・型番・サイズ・容量・枚数・現行品かどうかを確認する。同じJANの数量違いは合計の容量・枚数と総額を記録する。店舗受取は棚の価格とは区別し、受付停止や対応外の商品は掲載しない。

UIは標準的な日本語ゴシック。淡いピンク・黄色、白い余白、実際の商品写真、短い一般的なメニュー名を使う。抽象的な宣伝文や同じ意味の補足を増やさない。国内の育児サイトを参照した方針は docs/DESIGN_GUIDE.md を参照。

## GitHubからのSNS投稿の取り込み

`POST /api/refresh` はRSSと並行して、専用リポジトリ `tsushidayo/kosodate-biyori` の `collections/index.json` を読み取る。対象は `schemaVersion: 1`、`updatedAt`、`files` を持つ一覧。`files` に登録された `collections/YYYY-MM-DD/ファイル名.json` だけを取得し、既存の超教科書は参照しない。

各ファイルの `collectedAt` と `posts` を確認し、投稿ID・投稿URL・投稿者・投稿日・反応数・本文の形式が正しい投稿を「SNSの話題」へ加える。表示用には本文冒頭50字の見出しと110字の抜粋を使い、全文を転載しない。いいねと表示の数値は `recordedMetrics` に、取得時刻は `collectedAt` に残す。収集時点の記録であり、現在の順位や最新の反応数とは扱わない。投稿内容をサイトの医療上の助言として扱わない。

同じIDまたはXの投稿URLは重複させず、取得日時が新しい記録を優先する。既存のSNS項目も維持する。ファイルは最大20件、1件600KB、合計8MB、各取得は7秒まで。取得先は固定で、外部URL・親ディレクトリへの移動・転送先の取得は認めない。RSSと合わせて最大33件の外部リクエストとなる。

一覧やファイルの取得・解析が失敗した場合、SNS欄は更新前の内容を維持する。更新結果の `github` に `ok`、取得できた `files`、新規の `added`、`error` を記録する。RSSが取得できればニュース・コラムは引き続き更新する。定期処理からの既存の `/api/refresh` 呼び出しにも、この取り込みが含まれる。
